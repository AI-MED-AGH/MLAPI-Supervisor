## Project overview (derived from issues)

**MLAPI-Supervisor** is being designed as a **local control-plane service** for ML model deployments, centered around:
1. **Model/project registration and secure credential storage**
2. **Image update orchestration from GHCR to Kubernetes**
3. **Cluster monitoring + webhook-based notifications**
4. **CI/CD-driven refresh triggers from model repositories**

### Core product intent
The supervisor acts as an intermediary between:
- external ML model repos publishing Docker images to GHCR,
- the local container runtime/K8s cluster,
- and external observers (dashboards/bots) that need status events.

It follows an **Observer pattern**:
- model projects are registered once (including GHCR token),
- later a public endpoint is triggered with only `project_id`,
- supervisor pulls image + updates deployment, and emits notifications.

## Functional architecture inferred from issues

### 1) Foundation / Core data layer (Issues #14, #15, #17; older #13 replaced)
- **FastAPI app** with professional module layout.
- **Persistence** via SQLAlchemy + Alembic (SQLite or PostgreSQL).
- **Project entity**: name, image URL/name, GHCR token (encrypted), timestamps.
- **Endpoints**:
  - `POST /projects`
  - `GET /projects/{id}` (without exposing token)
  - `DELETE /projects/{id}`
- **Security requirement**: token encrypted at rest (cryptography-based util).

**Interpretation:** This is the system of record for model metadata and secret material needed for autonomous pulls.

### 2) The Orchestrator track (Issues #6–#9)
- Build `K8sService` and connect through local kubeconfig/k3s config.
- Implement pull trigger endpoint (GitHub Actions caller path with `project_id`).
- Pull authenticated image from GHCR locally.
- Patch K8s deployment container image (`spec.template.spec.containers[0].image`).
- Ensure rolling update behavior.
- Make pull+patch flow atomic with strong failure handling and logs.

**Interpretation:** This is the deployment automation engine translating “new image exists” into “running model updated in cluster”.

### 3) The Watchman track (Issues #10–#12)
- Register observer webhooks (`POST /observers`).
- `NotificationService` sends events to all observers (httpx).
- `GET /status/models` returns model runtime snapshot (status, replicas, resource usage).
- Background worker loop (60s) detects unhealthy states (CrashLoopBackOff/ImagePullBackOff) and state changes.

**Interpretation:** This adds operational observability and external integration; turns supervisor into an event producer, not just an API.

### 4) End-to-end workflow validation (Issue #17)
- Build sample model repo using fastmlapi.
- Publish image to GHCR.
- Add GitHub Actions workflow to call supervisor refetch endpoint after deploy.
- Add utility script for registration bootstrap.

**Interpretation:** This is crucial productization work: proving the external contract that other AI-MED member repos will reuse.

## Strengths of current plan

- Clear modular decomposition into **data/security**, **orchestration**, **monitoring**.
- Good attention to **secret handling** (encrypt GHCR token, avoid sending repeatedly).
- Realistic deployment model for **on-prem/local K8s**.
- CI/CD integration through GitHub Actions creates a repeatable, organization-friendly workflow.
- Observer/webhook architecture aligns well with operational tooling integration.

## Risks / gaps visible from issues

1. **Authn/Authz for public trigger endpoint**
   - The design intentionally allows `project_id`-based calls; hardening details are not yet explicit.
2. **Idempotency & concurrency**
   - Pull/patch operations need locking/de-dup if multiple workflow calls arrive.
3. **Token/key management**
   - Encryption-at-rest mentioned, but key rotation and key source strategy are unspecified.
4. **Observability depth**
   - Logging required, but no explicit metrics/tracing standard in issues.
5. **Schema evolution**
   - Alembic planned, but no migration/versioning conventions documented.
6. **Failure recovery**
   - Atomicity requested; rollback and retry policy not fully detailed.
7. **Compatibility assumptions**
   - Runtime choice (`docker-py` vs `subprocess` / `ctr`) still a research item, may affect portability.

## Practical “project definition” in one sentence

**MLAPI-Supervisor is a FastAPI-based local control service that securely stores model registry credentials, orchestrates GHCR-to-Kubernetes model rollouts via CI/CD triggers, and exposes cluster health/events through snapshot and webhook notification APIs.**
